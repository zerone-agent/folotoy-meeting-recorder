# 会议录音卡：基于官方参考项目的实现方案与验证计划

2026-10-29。本文是方案和资料核查，不是已实现或已通过硬件验证的设计。需求：断网时继续录音，联网后上传，服务端自动转写并在会议结束后生成纪要。目标离线时长、部署环境和纪要查看入口待定。

## 参考项目能提供什么

[官方参考项目](https://github.com/FoloToy/ai-passport)的 main 是硬件测试基线，非完整应用；可复用 BSP 和非 UI 逻辑，应用应重新设计界面。其 [Agent 指南](https://github.com/FoloToy/ai-passport/blob/main/AGENTS.md)指定 ESP32-C3、8 MB Flash、无 PSRAM、ESP-IDF 5.5.3；音频和存储等慢操作放工作任务，按键回调不可阻塞。项目默认分区为 NVS、PHY 和一个占剩余空间的 factory 应用：**默认布局没有独立录音数据分区**，需要为本应用重新规划并验证分区。

[硬件指南](https://github.com/FoloToy/ai-passport/blob/main/docs/hardware-design/AI_HARDWARE_DEVELOPMENT_GUIDE.md)和 BSP 提供音频接口；是否满足持续编码、写入和联网并发仍须实测。主仓库 Wi-Fi 扫描示例不等于已经实现本应用的配网和上传。

## 可借鉴的录音实现与容量

社区 [soundcore 固件](https://github.com/lewangdev/ai-passport-soundcore)作者描述：ES8311 采集，16 kHz 单声道 Opus，16 kbps，LittleFS；其代码地图列出 `sc_audio`、`sc_store`（含断电恢复）、`sc_core` 等。它模拟第三方录音设备及客户端协议，不是我们的服务端方案；复用前需逐文件审查依赖、许可、录音文件格式和恢复行为。

该项目的 [分区表](https://github.com/lewangdev/ai-passport-soundcore/blob/feature/soundcore-d3200-emulator/partitions.csv)分配 0x300000 字节给应用、0x4F0000 字节给录音。按 16 kbps 裸音频计算，0x4F0000 / 2000 / 60 ≈ **43 分钟的理论上限**；文件系统、封装和预留空间会减少容量。作者称约 40 分钟，尚未由本次复现。若 20 ms 帧在存储中每帧固定占 160 字节，则实际 64 kbps、上限约 10.8 分钟；README 仅说明协议以 160 字节单元承载帧，不能据此认定磁盘布局。应检查代码并通过写满测试测量，避免把编码码率当成实际存储速率。

## 建议架构（待选择）

设备：按键开始/结束 → 采音工作任务 → 编码 → 分段持久化；网络恢复后异步上传。每段带会议 ID、序号、长度、校验值；服务端持久化并确认后，设备才标记可删除。结束标记和所有分段确认后才触发处理。重启时恢复已提交数据，提示未完整结束的会议；空间不足及时提示并停止，不覆盖未上传录音。存储格式、断电丢失窗口、闪存磨损和并发性能必须通过实验确定。

服务端：接收并校验分段，按会议组装，异步执行 ASR，再用模型生成纪要；保存任务状态、失败原因和重试记录。模型服务、音频保留期限和结果入口尚未选定。

替代方案：手机在附近时通过蓝牙接收并离线存储，可扩展时长，但需要处理手机断连；外部存储有望支持更长会议，但硬件连接和兼容性未确认。是否需要转向这两种方案取决于目标时长和独立使用要求。

## 先验证离线录音和存储

1. **基线**：固定官方和社区参考项目的提交版本，确认依赖、分区、固件尺寸和干净构建；遵循官方验证脚本。当前尚未获取本地参考项目或执行构建。
2. **代码核查**：检查 `sc_audio` 和 `sc_store` 的帧编码、实际写入单位、文件头、同步频率和恢复算法；计算分区可用空间，不假设作者宣称的时长适用于新固件。
3. **录音写满**：在断网状态录制到容量阈值，导出并解码，测量有效时长、实际字节/秒、遗漏和损坏；分别测试安静、多人、远距离语音。
4. **断电恢复**：在写入不同阶段断电重启，核对已持久化音频、最后损失时长和索引恢复；重复测试并记录结果，不以文件存在代表内容完整。
5. **资源与续航**：连续采集/编码/写入时记录堆内存低水位、任务耗时、掉帧、温度和电池续航；验证网络恢复、上传与录音并发是否影响采集。
6. **上传完整性**：模拟断网、重复请求、服务端确认丢失和乱序；校验重试幂等、不提前删除、结束事件等待缺段，重组后可解码且音频完整。

每次记录硬件版本、固件提交、分区表、编码参数、录音环境和测试方法；区分构建、主机测试与实机测试。刷机前按[官方教程](https://ai-passport.folotoy.cn/guides/create-a-play-with-codex/)确认设备及恢复方式，并取得用户授权；合并镜像可能影响设备已有数据。

## 源码核查补充（2026-10-29）

通过 GitHub 文件接口读取社区项目默认分支：`main/sc_audio.c` blob `3af4d0331a315b0b97a0e1e71c54ea2d0bb85076`、`main/sc_store.c` blob `7ca45878221709528b928daf63486e7d8f880b4e`；这两个是文件对象哈希，**不是仓库提交版本**。本地克隆因网络不可用未完成，尚不能确认两个文件来自同一固定提交，也不能进行构建或主机测试。

- [采集实现](https://github.com/lewangdev/ai-passport-soundcore/blob/feature/soundcore-d3200-emulator/main/sc_audio.c)：调用 BSP 音频读取，Opus VOIP、可变码率、DTX 关闭、SILK 模式，逐帧回调。
- [存储实现](https://github.com/lewangdev/ai-passport-soundcore/blob/feature/soundcore-d3200-emulator/main/sc_store.c)：每帧写入 1 字节长度加实际编码数据，并非固定写入 160 字节；每 50 帧同步一次，并根据环形缓冲情况可能提前同步。另有 96 字节头和索引、文件系统开销。编码码率设定为目标值且启用 VBR，实际存储速率需测量。
- 恢复时扫描未正常结束的文件，计数完整长度记录、重建索引、回写头；不检查音频帧校验值，且同步调用的返回值未检查。挂载配置 `format_if_mount_failed = true`，挂载失败可能触发格式化，不能视为可靠数据保护。断电损失窗口及恢复成功率尚未实测，不能保证至多损失一秒。

结论：理论估算可用作容量级别判断，实际录音时长和断电恢复能力仍未核实。正式方案应禁止自动格式化已有数据、检查写入与同步错误并验证恢复。

## 60 分钟容量初步测算

用户目标至少 60 分钟连续离线录音。官方基线标注 8 MB Flash、无 PSRAM；实机刷写识别为 ESP32-C3、Embedded Flash 8MB (XMC)，不是仅根据分区设置猜测。soundcore 的应用分区 0x300000 字节、录音分区 0x4f0000 字节；实测的 47:13.96 录音 `.dat` 为 5,103,157 字节，平均约 1,801 字节/秒（包含帧长度和文件头，不包含索引和文件系统开销）。如果同样平均速率延续 60 分钟，`.dat` 约 6,482,577 字节，超过现有 5,177,344 字节录音分区；音频内容和 VBR 造成实际码率变化，不能视为保证值。

现有分区录 60 分钟，全部文件及文件系统平均写入预算不超过约 11.51 kbps，实际编码目标还须低于此值以留空间、元数据及恢复余量。当前编码目标为 16 kbps VBR，不能据目标直接推算实际；降低码率和调整分区可以探索，但需测试语音质量、ASR、文件系统最小余量、复杂声源最坏情况和连续 60 分钟实机，不保证必然可达。当前 soundcore 固件构建应用约 1.94 MB，可探索缩小其 3 MiB 应用分区；新的 Wi-Fi/上传固件实际体积尚未知，不能把现有镜像空余全部承诺给录音。
