# 会议录音卡服务端方案：Agent Runtime、ASR 和纪要

状态：待评审。本文是设计和有限模型探测，不代表服务端已实现或端到端验证。以本机 `zerone-agents/agent-runtime` 检出提交 `51cf183c56b0e0b493c70ab37f783f667a331ce0` 为源码核对基线；未刷新远端，不声称该提交是最新版本。

## 推荐结构

```text
设备 --HTTPS/分块--> Agent Runtime 宿主上的会议业务路由
                         |-- 设备认证、块校验、可靠存储、待处理任务
                         |-- StepFun ASR SSE 适配器 -> 转写
                         `-- 纪要工作器 -> Agent Runtime / Agent SDK -> StepFun 模型
                                                                  |
                                                         结果、证据与状态
```

服务使用 `@zerone-agent/agent-runtime` 的 `createRuntime()`，在 `host.app` 挂载独立 Hono 业务路由，由宿主启动 HTTP 和管理关闭；参考该版本 [SDK 使用说明](https://github.com/zerone-agents/agent-runtime/blob/51cf183c56b0e0b493c70ab37f783f667a331ce0/docs/sdk-usage.md) 与 [自定义路由示例](https://github.com/zerone-agents/agent-runtime/blob/51cf183c56b0e0b493c70ab37f783f667a331ce0/examples/programmatic/index.ts)。需要 Node.js 22+、TypeScript；是否直接调用已注册 Agent 或由业务工作器调用 SDK，实施前以可控输出、取消、失败语义及测试确定，不能只因示例存在就宣称集成通过。

**边界：** 当前 runtime 的 `RunRegistry` 是内存态，SSE 客户端断开会取消运行，且不提供持久任务、重试或事件回放；现有文件上传是聊天附件、容器生命周期，特定安全路径依赖 Linux `/proc/self/fd`，不适合直接作为设备可恢复上传或 Mac 本地持久录音存储。会议业务负责自己的文件/元数据持久化、任务租约、崩溃恢复、状态和幂等；不把 runtime run ID 当会议 ID 或把 SSE 活着等同任务可靠。来源：[runtime README](https://github.com/zerone-agents/agent-runtime/blob/51cf183c56b0e0b493c70ab37f783f667a331ce0/README.md)。

## 上传与工作流

自定义路由承载配对后的设备认证、创建会议、提交块、查询已接收块、最终清单和取消等操作。协议版本、请求大小上限及错误码实施前冻结；设备 ID、会议 ID 与序号的唯一约束、校验和及持久状态确保重试幂等，不允许不同内容覆盖同一块。服务端先持久化音频及清单，确保音频可跨重启恢复，再将会议记录与待处理状态在数据库事务内提交；只有两者均满足持久性要求才返回最终确认。文件系统与数据库不是同一事务，必须实现发布前后崩溃的孤儿文件和未完整事务清理/恢复，并以故障注入验证。设备收到最终确认后才自动删除本地音频。

处理工作器将自有会议状态从 `queued` 经租约推进到 `asr_running`、`minutes_running`、`completed` 或可重试/终止失败；重启回收过期租约并幂等重试。外部模型调用的超时或连接断开可能已经消耗费用，不能假定服务商请求恰好一次；记录尝试标识、结果提交去重与次数预算。截断、中断、用户结束的语义与删除并发遵守[主设计](superpowers/specs/2026-10-29-meeting-recorder-design.md)。

安全：设备业务路由的认证、管理员身份和授权要独立设计并验证。runtime `/v1/*` 的全局 API key 可选，未配置时开放；挂载 `/custom` 等路径不能假设受到该中间件保护。HTTPS 终止、证书信任、逐设备凭据及本地管理身份均需独立落实；不能将单个共享 runtime key 视作逐设备撤销。自定义路由的关闭排水、限流、上传尺寸、文件权限与生命周期也必须显式实现，不能假定继承内置 `/v1/*` shutdown gate。保留期限尚未确定，初版必须支持配置、可见状态与删除，不擅自定默认生产期限。

## 租约、删除和资源授权

**租约隔离。** 每次领取或接管阶段任务，数据库原子递增该会议阶段的租约代次并绑定随机令牌、到期时间。续租、阶段转换和结果发布均在同一数据库事务中条件检查会议未删除、阶段匹配、令牌与代次仍为当前值且租约未过期；条件不满足即丢弃返回结果，不更改状态。外部调用与临时产物按尝试隔离，只有条件提交成功才成为可见结果；旧工作器不得覆盖或删除新工作器产物。不可中断的外部请求可能继续运行和计费，但晚到结果不能发布。租约时间采用服务端数据库时钟；超时、续租失败与恢复均有界记录。验收注入 A 租约过期、B 接管并完成后 A 晚返回、续租失败、重复提交、并发接管及数据库事务崩溃，断言仅当前代次可发布。

**服务端删除。** 删除已确认会议须由有权限的用户或管理身份明确发起；这是服务端会议及关联数据的删除，不等同设备取消未完成上传或删除设备副本。数据库先原子持久化 `deleting` 墓碑、递增删除代次并撤销任务租约；此后拒绝读取敏感内容、创建新任务及结果发布，重复删除幂等。尽力取消在途 ASR/纪要请求，不等待外部服务承诺取消；所有晚到响应都必须通过上述数据库条件提交而被拒绝。后台有界清理音频、块、转写、纪要、索引、任务产物和临时文件，校验清理结果后标记 `deleted`；失败保持可见失败状态并重试，重启扫描 `deleting`。外部 ASR/模型供应商副本、日志与备份不假定即时删除：须记录适用供应商政策、日志不含正文/音频、按明确保留策略处理备份并在恢复时应用墓碑防止复活；保留期限和法律要求待产品确定，不能宣称已经完成远端或备份擦除。验收在上传完成、ASR、纪要、结果发布、清理各阶段删除，并注入崩溃、重复删除、供应商晚返回与备份恢复。

**资源归属与授权。** 服务端依据已认证设备身份和服务端配对关系绑定会议归属，不信任请求中自报设备 ID。每次创建、查询块、写块、提交清单、确认状态和取消均检查设备归属与操作权限，其他设备不能读取、追加或取消；用户查看、导出、删除需要独立的用户/管理员授权。重新配对后的新凭据仅在管理员授权并完成原设备身份的明确绑定/迁移后继承既有会议访问权限，普通新设备凭据不自动继承；旧凭据撤销和离线待办遵守主设计。验收跨设备读写、取消、猜测 ID、已撤销凭据和重配前后权限迁移；不得在错误消息中泄露会议存在或内容。

## ASR：StepFun

初版以已实测可用的 `stepaudio-2.5-asr` 为提供商模型，使用已验证的 `https://api.stepfun.com/step_plan/v1/audio/asr/sse`，将设备私有 Opus 帧封装为标准 Ogg Opus 后一次发送，`language=zh`。仅收到 `transcript.text.done` 且结果经过合法性与保存检查才算该次转录完成；delta 用于进度，断流后重试应明确整个请求重做，避免拼接重复文本。密钥只由服务端安全配置注入，不进入仓库、设备固件、客户端或日志。

已有短读稿和 30 分钟合成三点标记测试；它们验证接口和特定样本覆盖，不证明真实 30 分钟会议的准确率、计费、并发及重试可靠性。[实测记录](../research/2026-10-30-stepfun-asr.md)。

## 纪要模型：初版选择

建议初版选择 **`step-3.7-flash`**，通过现有 Step Plan 服务端凭据接入；以参数配置而非硬编码，保留替换模型能力。2026-10-30 对该凭据可见模型做过一次虚构中文会议样例调用：`step-3.7-flash` HTTP 200、输出内容非空、`finish_reason=stop`，能保留负责人/时间待确认。对照 `step-5-preview` 同样 HTTP 200，但把“建议”表述成已决定的计划；`step-3.5-flash` HTTP 200 但该次 600 token 上限下内容为空且 `finish_reason=length`，不能评价其能力。单条合成样例不足以证明模型准确率、稳定性、速度或成本，也不代表 agent-runtime SDK 路径已跑通；只支持将 `step-3.7-flash` 作为可用的首选候选。测试没有发送真实会议内容，可能计费。

输出契约至少包含摘要、讨论、明确结论、待办（责任人和期限可为待确认）、待确认问题、是否截断及原因；区分建议与决定，不虚构负责人或日期。纪要必须引用转写片段或定位信息并提示自动转录可能有误；SSE 的 ASR 结果当前未验证音频级时间戳，不能伪造时间码。对长转写按边界分段、合并时保留原文引用并用证据校验；最终输出校验失败不得标记成功。应使用多个覆盖反例的合成样本、已有用户许可的真实测试样本进行回归，标记未经人工听校的文本，不把模型测试当生产验收。

## 逐字稿证据定位契约

每次保存 ASR 最终结果时生成不可变 `transcript_version_id`，规范化前后均保留可追溯文本和哈希；分段按版本生成稳定 `segment_id`，重试或重新转写产生新版本，旧纪要继续引用原版本。纪要的每条结论、待办和关键讨论须引用版本 ID、片段 ID、片段内 Unicode 码点的半开区间及原文摘录；校验版本归属、范围合法且摘录与该版本原文精确一致。分段合并以显式映射保留源片段和范围，不用重新生成的段落位置替代证据。ASR 尚无可靠音频时间戳时不得伪造时间。引用缺失、越界、版本错误或文本不匹配时结果进入待复核/失败，不标记完成；匹配只能证明文本位置存在，不能证明语义支持，仍须用建议与决定、否定和责任人缺失等反例样本评估及人工复核。验收重转写、分段合并、Unicode、引用失配及不同版本交叉引用。

2. 以 Node 22 的受控环境实现并测试：首次配网、分块上传、断线、重复块、最终确认前后崩溃、重试、删除与取消交错、ASR SSE 断流、纪要重试及可见结果去重。
3. 实际接入指定 SDK/runtime 与 `step-3.7-flash` 后，检查认证、token 上限与错误映射、最终输出完整性；目前只有独立 API 小样本探测。
